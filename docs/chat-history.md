# ChatHistory 后端接口

所有接口带 `/api` 前缀，采用项目已有的 `BaseResponse` 和 `Page` 响应结构。

## 应用对话历史

`POST /api/chatHistory/app/list/page`，仅应用创建者或管理员可调用。
首次请求：

```json
{"appId":"应用ID"}
```

默认最多 10 条，结果按照 `createTime DESC, id DESC` 排列。
每条记录包含 `id`、`appId`、`userId`、`message`、`messageType`、`createTime`、`updateTime`。
`messageType` 为 `user` 或 `ai`，AI 错误同样使用 `ai`，消息正文包含 `[生成失败]` 和错误原因。

向前加载时，使用上批返回的最后一条（最早的消息）作为游标：

```json
{
  "appId":"应用ID",
  "pageSize":10,
  "lastCreateTime":"2026-10-07T00:00:00",
  "lastId":"上批最早消息ID"
}
```

时间和 ID 必须一起传入；同一时间的消息通过 ID 区分。
应用历史接口不使用递增页号，`data.pageNumber` 始终为 1，
`data.totalRow` 表示当前游标范围内剩余的消息数量。
`totalRow > records.length` 时可以继续向前加载；空数组表示没有更早的消息。
所有 Long ID 均按项目配置序列化为字符串，前端应保留字符串以免丢失精度。

聊天页面对接流程：

1. 读取应用详情后，仅创建者和管理员请求历史；其他访客保留网站预览和只读输入框。
2. 首批有历史时，将 `records` 反转为时间正序展示，不再自动发送初始化提示词。
3. 首批无历史时，仅创建者可以自动发送应用的初始化提示词。查询失败不能按“没有历史”处理。
4. 向前加载时，反转新批次的记录并插入消息列表顶部，保留现有滚动位置。

## 管理员监管查询

`POST /api/chatHistory/admin/list/page`，要求管理员角色。

```json
{
  "pageNum":1,
  "pageSize":10,
  "appId":"可选应用ID",
  "userId":"可选用户ID",
  "messageType":"ai",
  "message":"可选内容关键词"
}
```

支持按消息 ID、应用 ID、用户 ID、消息类型、内容关键词筛选。
不传过滤条件即可查看所有应用的历史；服务端固定按时间和 ID 降序排列，忽略客户端排序参数。

## 消息写入与清理

`GET /api/app/chat/gen/code` 的请求和 SSE 事件格式保持原样：
用户消息先保存，完整 AI 回复在生成和文件保存成功后保存，再发送 `done`。
AI 同步启动失败、流式失败、文件保存失败或空回复都会保存错误信息；
流式失败还会保留已经返回的内容，再发送 `error`。
历史保存失败不会返回成功完成事件。

删除应用时在同一数据库事务中逻辑删除该应用的全部历史，和 App 模块保持一致。
没有历史记录也可以正常删除应用；数据库操作失败会回滚数据库变更。
历史写入与应用删除会锁定同一应用行，防止已删除应用再次产生可见历史。
现有的文件清理仍使用本地文件系统操作，不属于数据库事务。

通用的历史新增、更新和删除接口没有对外开放，客户端通过正常对话流程生成记录。
